# Pantry — MVP spec

> **Name decided (Kris, 26 Oct 2026): Pantry**, issue key `PAN`, token prefix `pan_`. Final pre-build check done 26 Oct 2026 (Europe/Athens). This is the build copy: the research log, market check and competitor notes live only on the spec Page. Any open question in §12 that Kris hasn't answered is built with its ★ default.

## 1. Pitch and who it's for
A fast, keyboard-first, open-source issue tracker (MIT, non-commercial) for 1–3 person teams working with AI coding agents. First users: Kris and his wife, running their own products, moving off Linear. Agents stay outside the tool: you point one (Cursor, Claude Code, …) at an issue key and it reads and updates the issue through an MCP server.

## 1b. What makes it different (problems we solve)
1. **Trackers are built for companies; solo builders and 1–3 person teams pay in complexity.** No teams, triage, analytics, estimates or permissions: just issues, spaces and projects, views and speed.
2. **AI agents work from scattered context.** Each space has a context doc that agents read first, and the MCP server gives any agent the issue, its sub-issues, comments and space context from just an issue key.
3. **Agent work is invisible or spread across tools.** Agents comment and move status on the issue through MCP, acting as you and tagged "via MCP", so the tracker stays the source of truth.
4. **Lock-in and cost.** Free and MIT-licensed; your data lives in your own Vercel and Convex accounts; a one-click deploy of about 5 minutes that fits the free tiers for small teams (Vercel Hobby is non-commercial use only); no hosted plan.
5. **Web trackers feel slow or heavy.** A keyboard-first web app with Convex realtime and optimistic updates in v0.1, then a polished Tauri Mac app in v0.2 (phase 2).
6. **Trying a self-hosted tool takes setup.** A live demo at launch, then local mode in v0.2 with no accounts.
7. **Later: agency work and product building in one tool.** Client vs Product mode.

## 2. Principles
- **MVP first.** v0.1 ships only what two people need to leave Linear.
- **Agents stay outside the tool.** They connect over MCP and act as the user who owns the token.
- **Keyboard first, instant UI.** Realtime Convex queries + optimistic mutations; every core action has a shortcut.
- **One backend, thin surfaces.** All logic lives in Convex functions; web UI, Mac app and MCP are adapters over it.
- **Self-host in minutes.** Your own Convex backend + one small Vercel app.
- **Fixed stack:** Next.js App Router, Convex, Vercel, TypeScript, Tailwind, shadcn/ui on Base UI with our own design system; Tauri + React for the Mac app.

## 3. MVP features (v0.1)
- One workspace per instance with its human members; invite links tied to an email address (you copy and send the link yourself; v0.1 sends no email).
- **Spaces** (Workspace → Space → Project → Issue, decided by Kris 26 Oct 2026): a space is one of your products or one client ("Pantry", "Acme Ltd"), with a key (e.g. `PAN`), the issue counter, a **space context doc** (markdown) agents read over MCP, and the list and board views. Issue keys stay `PAN-42`.
- **Projects** inside a space: optional workstreams ("LinkedIn", "Marketing", "Launch"): a name, an optional colour, an order and an archive flag. An issue is in at most one project.
- Issues: title, markdown description, status, priority, assignee, labels, due date, sub-issues (`parentId`, one level).
- Six default statuses per workspace, one per category: Backlog (backlog), Todo (unstarted), In Progress (started), In Review (review), Done (done), Canceled (canceled). Rename, recolour and reorder only; no adding or deleting in v0.1.
- List view and board view per space, grouped by status or by project; "My issues"; simple filters (status, assignee, label, priority, project) kept in URL params and applied client-side, not saved.
- Issue detail with comments and an activity log.
- Command palette + keyboard shortcuts.
- **Personal API tokens** + a minimal **MCP server** that acts as the token's owner.
- **Cloud setup as close to one click as possible** (§10): Deploy button → Vercel + Convex, secrets generated by the build, first sign-up becomes owner.
- Web app on Vercel (M1–M4), then the landing page and live demo for launch (M6). The Tauri Mac app (M5) moved to v0.2 (Kris, 27 Oct 2026).

## 5. Convex data model
Users/sessions/accounts live in the Better Auth Convex component's tables; our tables reference its user id. **Exact schema: §10b** (source of truth; this table is the summary).

| Table | Key fields | Indexes |
|---|---|---|

| `members` | workspaceId, userId (Better Auth user id), displayName, avatarUrl?, role: `owner`\|`member` | `by_workspace`, `by_user`, `by_workspace_and_user` |
| `invites` | workspaceId, email (lower-cased), tokenHash, createdBy (→members), expiresAt, acceptedAt?, revokedAt? | `by_token_hash`, `by_email`, `by_workspace` |
| `spaces` | workspaceId, name, key (`PAN`), nextIssueNumber, archivedAt?, kind? (`product`\|`client`, product when missing) | `by_workspace`, `by_workspace_and_key` |
| `projects` | workspaceId, spaceId, name (unique per space, ignoring case), color?, sortOrder, archivedAt? | `by_space`, `by_space_and_name` |
| `statuses` | workspaceId, name, category (`backlog`\|`unstarted`\|`started`\|`review`\|`done`\|`canceled`), order, color | `by_workspace_and_order` |
| `labels` | workspaceId, name, color | `by_workspace` |
| `issues` | workspaceId, spaceId, projectId? (→projects, same space), number, key (`PAN-42`), title, description (md), statusId, statusCategory, priority (0–4), assigneeId? (→members), creatorId (→members), labelIds[], parentId? (one level), dueDate? (`YYYY-MM-DD`), sortOrder, completedAt?, updatedAt | `by_space_and_status`, `by_space_status_and_completed`, `by_project`, `by_assignee_and_category`, `by_parent`, `by_workspace_and_key`, `by_workspace_and_updated`, `by_space_and_updated`, `by_assignee_and_updated`; search index `search_title` |
| `comments` | issueId, authorId (→members), body (md), via (`app`\|`mcp`), editedAt? | `by_issue` |
| `activity` | workspaceId, issueId, actorId? (→members), type, from?, to?, via (`app`\|`mcp`) | `by_issue`, `by_workspace` |
| `docs` | workspaceId, spaceId?, kind (`space_context` in v0.1), title, body (md), updatedBy, updatedAt | `by_space_and_kind` |

Notes: created times use Convex's built-in `_creationTime` (no `createdAt` fields). Issue numbers come from `spaces.nextIssueNumber` incremented inside the create mutation (Convex mutations are transactional, so no duplicates). MCP actions are attributed to the token owner with `via: "mcp"`, which the UI shows as a small "via MCP" tag. The `views` table (saved views) is added in v0.2 together with its UI.

Forward-compatible, not built in v0.1: Client / Product modes later add optional `workspaces.mode` (spaces already carry `kind`; see Later versions).

## 6. MCP server
**Where:** `/api/mcp`, a Next.js route handler on Vercel.
**Auth:** personal API tokens created in User settings → API tokens. Shown once; stored as SHA-256 hash + short prefix. Sent as `Authorization: Bearer <token>`. The server acts as the token's owner; comments and changes show as that user, tagged "via MCP". Revocable; `lastUsedAt` tracked.
**Internal layer (not a product surface):** the route calls Convex functions in `convex/mcp.ts` via `ConvexHttpClient`, passing the token; each function hashes and checks it before doing anything. There is no public REST API in v0.1 (moved to later).

Tools (minimal):
| Tool | Does |
|---|---|
| `get_issue` | One issue by key, incl. its space key, project name, sub-issues, comments |
| `get_space_context` | The space's context doc (agents call it first) |
| `list_issues` | Filters: space, project, status/category, assignee (`me`), label, priority |
| `create_issue` | New issue in a space, optionally in one of its projects |
| `create_sub_issue` | New sub-issue under a parent key |
| `add_comment` | Comment on an issue |
| `update_issue` | Change status, priority, labels, assignee, project |

Typical use: create a token → add `/api/mcp` with the bearer token to your MCP client → tell the agent "work on PAN-42" → it calls `get_issue` + `get_space_context`, moves the issue through statuses itself with `update_issue` (nothing changes status automatically), posts notes with `add_comment`, adds follow-ups with `create_sub_issue`.

**Why Next.js and not Convex HTTP actions:**
- Vercel's `mcp-handler` v2 mounts in a Next.js route handler, serves the current stateless MCP spec (2026-07-28) and falls back to stateless Streamable HTTP for 2025-era clients; needs Node 20+ (npm README / Vercel changelog).
- Convex HTTP actions run in Convex's runtime without Node-specific APIs (Convex docs), so serving MCP there means hand-rolling JSON-RPC instead of using the maintained SDK.
- MCP authorization is OPTIONAL in the spec; HTTP servers that do implement it SHOULD follow the OAuth 2.1-based flow. v0.1 uses static bearer tokens (clients that accept custom headers); MCP OAuth later.

## 7. Auth
**Decided: Better Auth through the official `@convex-dev/better-auth` component**, email + password only in v0.1 (Q2 ★; GitHub OAuth or magic link only if Kris picks Q2 b/c). API tokens are our own table, not Better Auth sessions.
- Runs inside Convex (data in Convex), documented for Next.js and for client-only SPAs (cross-domain plugin, auth routes served from the `.convex.site` URL). The SPA mode is what a Tauri app needs, so one setup can serve web and Mac.
- Convex Auth's docs still label it **beta**. Better Auth's component is pre-1.0 (0.12.x on the Convex components page) and pins a Better Auth version, so pin both.
- Needs Convex ≥ 1.25.0, env `BETTER_AUTH_SECRET` and `SITE_URL` in Convex.
- Risk, spiked in M2 (task 2): sign-in from the Tauri app (trusted origins, cross-domain plugin); email + password avoids OAuth redirects in the webview for v0.1.

### Multiple instances (approved by Kris, 26 Oct 2026)
- **Concept:** each instance (its own Vercel + Convex) is fully separate: its own accounts and data, no sync or federation. Being invited to someone else's instance means creating an account on that instance. On the web, another instance is simply another URL.
- **v0.1 (data shape only):** the Mac app connects to one server, but stores servers as a list from day one, so the v0.2 switcher needs no migration:
  `servers[]: { id (uuid), url, name, convexUrl, convexSiteUrl, addedAt, lastUsedAt }` + `activeServerId`, in a plain JSON file via Tauri's official Store plugin (non-secret). Each server's session token goes in the **macOS Keychain**, keyed by server id. Tauri has no official Keychain plugin (its official secrets plugin, Stronghold, uses an encrypted file instead), so use the widely used `keyring` Rust crate (v4.2.0) behind two small Tauri commands (`session_get/set/delete`). Community plugins exist (`tauri-plugin-keyring`, `tauri-plugin-keyring-store`) but are unofficial.
- **v0.2: Slack-style server switcher** in the Mac app sidebar: add server (URL → `/api/instance` → sign in), per-server sign-in, `Cmd+1…9` to switch, per-server notifications and unread badges (each server keeps its own Convex client and subscriptions while the app runs).
- **Agents:** one personal token per instance, and each instance is its own MCP server entry in the agent client. Tell the agent which one to use ("use pantry-acme for ACME-12"). Example for Cursor's `mcp.json`:
  ```json
  {
    "mcpServers": {
      "pantry-home": {
        "url": "https://pantry-kris.vercel.app/api/mcp",
        "headers": { "Authorization": "Bearer ${env:PANTRY_HOME_TOKEN}" }
      },
      "pantry-acme": {
        "url": "https://tracker.acme-studio.com/api/mcp",
        "headers": { "Authorization": "Bearer ${env:PANTRY_ACME_TOKEN}" }
      }
    }
  }
  ```
  Claude Code: `claude mcp add --transport http pantry-home https://pantry-kris.vercel.app/api/mcp --header "Authorization: Bearer <home token>"`, and the same again for `pantry-acme`.

## 9. Self-hosting
- **The Mac app is a pure client** — no data in it; it connects to a server.
- **Each self-hoster deploys their own Convex backend.** The supported v0.1 path is Convex Cloud through the Vercel Marketplace integration (§10). The open-source self-hosted Convex backend (Convex docs: same code as the cloud service; licence FSL Apache 2.0) should also work but isn't tested in v0.1.
- **Plus the small Vercel app**: web UI + `/api/mcp`.
- **First launch of the Mac app:** asks for the server URL, then sign-in (details in §10).
- **Distribution:** signed + notarized DMG on GitHub Releases (Tauri docs: notarization needs a paid Apple Developer account).
- **Updates:** Tauri updater plugin with a static `latest.json` on GitHub Releases (generated by `tauri-action`); update bundles must be signed with a separate updater key — losing it means existing installs can't be updated.
- **Build from source:** clone, `tauri build` for an unsigned local build.

## 9b. Local mode (v0.2)
**Decided (Kris, 26 Oct 2026): local mode ships in v0.2 as a committed feature.** Framing: *use it for real before you bother hosting.* The Mac app runs fully on your machine with a bundled open-source Convex backend, for **one user with no login**, and moves to Convex Cloud or a self-hosted server when you're ready. Earlier verdict: feasible with caveats; the caveats below become the v0.2 work list. v0.1 does not depend on any of it.
- **Backend:** the official precompiled `convex-local-backend` runs without Docker. Release assets exist for `aarch64-apple-darwin` and `x86_64-apple-darwin` (~56 / ~60 MB zipped; 174 MB unzipped on arm64, measured). Data goes in SQLite + a local storage dir. Ship it as a Tauri sidecar (`externalBin`, binary named with the `-$TARGET_TRIPLE` suffix).
- **Keys/ports:** on first run the app generates a random instance secret, then `convex-local-backend keygen admin-key --instance-name … --instance-secret …` prints the admin key (subcommand in current backend source). Defaults: port 3210 (API), 3211 (HTTP actions), interface `0.0.0.0` — so pass `--interface 127.0.0.1`, pick free ports, and `--disable-beacon`.
- **Deploying functions (main risk):** the only documented path is the Convex CLI (`convex deploy` with `CONVEX_SELF_HOSTED_URL` + `CONVEX_SELF_HOSTED_ADMIN_KEY`), which needs Node. Plan: bundle a pinned Node runtime (Node 24 LTS darwin-arm64 binary = 123 MB, measured) + the `convex` package + our `convex/` source; run `convex deploy --typecheck disable --codegen disable` on first run and after every app update. No `"use node"` actions (local backends run them with the system's Node). Smaller alternative: replay a CI-built push against the CLI's internal `/api/deploy2/*` endpoints from Rust — undocumented, so only with pinned CLI/backend versions. First v0.2 task: prove this end to end.
- **No login:** a `LOCAL_MODE` Convex env var makes the viewer helper return the single local owner member; no Better Auth accounts exist locally. The local backend only listens on `127.0.0.1`.
- **Move to cloud:** set up the cloud instance (§10) first, then `convex export --include-file-storage` locally and `convex import --replace-all` into the target. Documents keep `_id` and `_creationTime`; `_storage` files keep their ids. Not included: code, env vars, pending scheduled functions. On the target, the first sign-up claims the imported local owner member (one-time claim code shown in the Mac app), so issues, comments and activity stay attributed. Import is labeled beta.
- **MCP:** a **local HTTP** MCP server on `127.0.0.1` run by the same Node sidecar with the same tool code, so agent config matches cloud (URL + bearer). The app generates the token and shows the config snippet. stdio-only clients can bridge via `mcp-remote`. Only works while the app is running.
- **Not available locally:** a second person (no invites, no web app), email. Data lives on one Mac → an "Export snapshot" button and a reminder to back up.
- **Cost:** ~+300 MB app per arch (backend + Node), per-arch DMGs; every app update must push functions and may run backend migrations; bundled binaries must be code-signed with the app.

### Appearance customisation (later, after v0.2)
**What MonoCode does** (read from its source on GitHub, `src/features/settings/model/appearance.ts` and `workspaceThemes.ts`, and its `src-tauri` config and CHANGELOG, main branch as of 23 Oct 2026):
- Colour scheme dark / light / system (default dark).
- 11 workspace theme presets, each with a dark and a light variant: Default, Harbor, Moss, Ember, Orchid, Tidepool, Dune, Rosewood, Glacier, Arcade, Ink.
- A custom accent colour (any hex, default none); the text colour on the accent is picked black or white by luminance.
- A theme tint: hue 0–360 (default 240), saturation 0–100 (default 0, so neutral grey), and dark-theme lightness 0–30 (default 9).
- Glass: sidebar opacity 0.15–1 (default 0.85) and blur 1–64 (default 24), on by default except on Linux, plus a "Transparent window" switch. On macOS it uses native blur (`NSVisualEffectView`, under-window background, behind-window blending) in a transparent Tauri window.
- A chat background image with opacity 0.05–0.65 (default 0.24), shown on empty screens only or everywhere, with optional effects (dither, ASCII, halftone, scanlines, haze).
- Also: UI scale, a colour-blind / high-contrast diff palette, and theme changes that sync across open windows.

**Ours, to match:**
- **Theme presets:** a handful of named presets (a neutral default plus a few tinted ones), each a dark and a light set of values for the existing token names (`--background`, `--card`, `--foreground`, `--border`, the neutral scale). No new token names, so Tailwind's `@theme inline` mapping keeps working unchanged.
- **Accent picker:** a few swatches plus a custom hex (default: none, monochrome per Q6 c). It sets `--primary` and derives its hover and subtle variants (with `color-mix`), with automatic black/white text on the accent. Status and priority colours stay fixed so they keep their meaning.
- **Neutral tint:** hue and saturation sliders applied to the neutral scale (default 0 saturation, the near-monochrome look).
- **Background:** none (default), or your own image behind empty states and the board with an opacity slider. Mac app first; on the web, opt-in.
- **Translucency (Mac app):** Tauri v2 `windowEffects` on a transparent window (Tauri's config lists macOS materials such as `sidebar` and `underWindowBackground`, and `liquidGlass*` on macOS 26+), with sidebar opacity and blur sliders and a "Transparent window" off switch. Respect the macOS Reduce transparency setting.
- **Where it's stored:** per user, on the device first (so it works offline and in the demo), synced to a user-preferences record later.

## 9d. UI stack: shadcn/ui on Base UI + our design system
**Decided (Kris, 26 Oct 2026): Arc UI is out of scope.** The stack is shadcn/ui only, on **Base UI** primitives (`@base-ui/react`), with our own design system on top. No licensed components and no registry tokens, so clones and CI build with nothing but the repo. Kris wants it **not to look stock shadcn**: the design system is real M1 work (task 4), not a polish pass.
- **Setup:** shadcn CLI 4.x in monorepo mode: a `components.json` in `packages/ui` and in each app; components live in `packages/ui/src/components` and are imported from `@pantry/ui`. ### Design system (M1 task 4)
Target: the Plane × MonoCode direction in §9c, with Linear's restraint. Dense, monochrome, small type, hairline borders, colour only in status/priority/label glyphs.
- **Type and density:** 13px UI text, 12px metadata, mono for keys (`PAN-42`), timestamps and shortcuts; list rows about 32px; tight, consistent spacing scale; small concentric radii; almost no shadows (borders and surface steps do the separating).
- **Colour:** the 12-step grey scale carries both themes (dark is the hero look; light is a first-class peer) and the monochrome primary (near-black in light, near-white in dark); fixed status and priority colours; label colours user-picked from a curated set. No accent hue (Q6 c).
- **Focus:** a visible ring for keyboard focus (`:focus-visible`) only, none on pointer focus.
- **Our own small components:** status glyph, priority glyph, label chip, issue key, keycap (on shadcn Kbd), avatar stack.
- **Review surface:** a dev-only `/design` route in `apps/web` that renders every token and component in light and dark. Kris approves the look there before M2 screens are built.

### Motion (keep Arc's feel)
Kris liked Arc's motion, so we rebuild the same feel ourselves with `motion` (`motion/react`), from its public docs only, never its source.
- **Tokens** (`packages/ui/src/lib/motion.ts`, plus matching CSS variables): springs `smooth` (~0.4s, no bounce: panels, heights, drawers, sidebar width, anything that reports state), `snappy` (~0.26s, slight bounce: presses, small indicators, icon swaps), `morph` (~0.42s, slight bounce: shared highlights via `layoutId`); tween durations instant / fast / exit / standard (0.12 / 0.16 / 0.18 / 0.24s) with enter and exit eases.
- **Rules:** animate `transform` and `opacity`; one continuous movement per state change; springs for anything the user can reverse, so it's interruptible; exits faster than entrances; presses scale to ~0.97 except elements that anchor a menu or popover; no scroll reveals or decorative loops in the app.
- **Where:** dialog, popover and menu enter/exit; the selection highlight gliding between list rows, tabs and segmented controls; sidebar fold; board card drop and list reorder; toasts.
- **Reduced motion:** every animation has a `useReducedMotion` branch that keeps the end state, focus and feedback and drops the travel.

### Command palette (keep Arc's feel, M3 task 2)
Built on shadcn's Command (cmdk inside a Base UI dialog), extended to behave like Arc's:
- **Motion:** the panel rises in on a spring; the results frame springs to the list height as the query filters; one highlight glides to the active row (`morph`) on arrow keys and hover; rows glide on small shifts and snap on long jumps.
- **Matching:** every query word must match: anywhere in the label, at a word start in the description or keywords, or as letters in order ("shpr" finds Share project). Label prefixes rank first, groups follow their best match, matched letters render in medium weight. This replaces cmdk's default filter (`shouldFilter={false}` + our ranking). Issue results come from debounced `issues.search`, with an exact key match first.
- **Keyboard and a11y:** first result active as soon as results show; Up/Down, Home/End, Enter; Esc clears the query, then closes; keycap shortcut hints per row from the shortcut registry; a polite live region announces the result count.
- **Groups:** Issues, Spaces (spaces and their projects; a project opens its space filtered to it), Navigation, Actions.

### Sidebar (keep Arc's feel, built on shadcn Sidebar)
- shadcn Sidebar as the base, collapsible to an icon rail with tooltips; a Sheet below ~640px.
- Width springs between full (~272px) and rail (~56px) through one motion value, so lists don't re-render; collapsed state saved per user on the device.
- `[` folds and unfolds the rail, registered in the shortcut registry (ignored in inputs, menus and dialogs), replacing shadcn's default `Cmd+B`.
- Contents: workspace name and user menu, search (opens the palette), My issues with a rolling count, the spaces with coloured dots and inline "New space", each expanding to its projects (a project opens the space's list or board filtered to it, `?project=<name>`), settings. The active-item highlight glides (`morph`). Draggable favourites are not in v0.1.

### Markdown editor
Descriptions, comments and space context docs are stored as markdown, because agents read and write them over MCP, so the editor must round-trip markdown. ★ **Tiptap 3** (`@tiptap/react`, `@tiptap/starter-kit`, `@tiptap/markdown`) behind one `MarkdownEditor` in `packages/ui`, styled to our tokens; the same component renders read-only content.
- Supports headings, bold/italic/strike, inline code and code blocks, links, bullet/ordered lists, blockquotes; markdown shortcuts as you type.
- Round-trip fixtures (including agent-written markdown) must load and save unchanged when untouched; anything Tiptap can't represent must survive as-is rather than be dropped.
- Saves on blur and `Cmd/Ctrl+Enter`, never per keystroke: each description save writes an activity row. Comments submit with `Cmd/Ctrl+Enter`; `Esc` leaves the editor.
- Not in v0.1: mentions, slash commands, images or file uploads.

## 10. v0.1 cloud setup
Goal: a fresh instance in **about 5 minutes, under 10** including creating Vercel and Convex accounts. One Deploy button, one Vercel form, then sign up in your own app. Checked against Vercel and Convex docs on 26 Oct 2026.

**What the Deploy button does** (Vercel Deploy Button docs; Convex's own template uses the same pattern):
- The README button is a `vercel.com/new/clone?repository-url=…` link. Vercel **clones the repo into the user's GitHub account** (a copy, not a GitHub fork) and creates a Vercel project.
- The link adds the Convex Marketplace integration as a product (`integrationSlug: convex`, `productSlug: convex`; Convex's template passes it in a `products=` param, Vercel's docs document the same shape under `stores=`). This **provisions a new Convex project** (Marketplace projects sit in their own Convex team, billed through Vercel) and **syncs `CONVEX_DEPLOY_KEY`** into the Vercel project for Production and Preview. The integration needs Production + Preview enabled and an empty "Custom Prefix" (Vercel Marketplace Convex page).
- `vercel.json` sets the build command, so nothing is typed by hand. Convex's template uses `npx convex deploy --cmd 'npm run build'`; ours wraps it in `scripts/vercel-build.sh`.

**What `scripts/vercel-build.sh` does on every build:**
1. If the Convex deployment has no `BETTER_AUTH_SECRET`, generate one (`openssl rand -base64 32`) and set it with `npx convex env set`. It's never shown, never stored in Vercel, and survives redeploys.
2. Set Convex `SITE_URL` to `https://$VERCEL_PROJECT_PRODUCTION_URL` (a Vercel system variable available at build time: the shortest custom domain, else the `vercel.app` domain), so adding a custom domain fixes itself on the next deploy.
3. `npx convex deploy --cmd-url-env-var-name NEXT_PUBLIC_CONVEX_URL --cmd '<derive NEXT_PUBLIC_CONVEX_SITE_URL (.cloud → .site), NEXT_PUBLIC_SITE_URL; build apps/web>'`. Per Convex's CLI help, deploy runs `--cmd` with the deployment URL set, typechecks, pushes functions, schema and indexes, and stops at the first failure.
- **To verify in M1:** that the Marketplace-synced deploy key has the `deployment:env:view` and `deployment:env:write` actions (Convex's [Role Actions](https://docs.convex.dev/team-management/role-actions) list them separately from `deployment:deploy`; checked 26 Oct 09:58, still not documented for Marketplace keys), so it may run `convex env get/set`. Convex's Deploy Keys page (checked 26 Oct 08:05) says dashboard-made keys pick their actions, `deployment:deploy` for CI and separate permissions for reading/writing environment variables; it doesn't say which actions the Marketplace key gets. Fallback: the first-run screen shows a one-line `npx convex env set BETTER_AUTH_SECRET …` with a generated value.
- **Also to verify in M1:** the monorepo build from the clone. Default (§10b): Root Directory `apps/web` with `apps/web/vercel.json`, as in Convex's own Turborepo template. **Checked 26 Oct 08:05:** the Deploy Button docs list only `repository-url`, `project-name`, `repository-name` and `stores` (plus env params); there is no Root Directory parameter, and a subdirectory in `repository-url` clones only that folder, which would drop `packages/*`. So the button cannot set Root Directory. M1 tries, in order: (1) the README tells the user to set Root Directory to `apps/web` in the clone form (one field, shown in a screenshot); (2) if that field isn't offered, a root-level `vercel.json` that installs with pnpm and builds `apps/web` via the wrapper script. Pick whichever passes the fresh-account test; don't fork the repo into a `deploy/` template.

**What the user still does:** create or sign in to Vercel (with GitHub) and accept the Convex integration. No secrets to type in v0.1: no email provider, no OAuth app (GitHub OAuth would need a GitHub OAuth app's id + secret, only if Kris picks Q2 b).

**First run:**
1. Open the new `*.vercel.app` URL → a setup screen (only while the instance has no members) → the **first sign-up becomes workspace owner**; default statuses and a sample space (`PAN`, no projects) are created.
2. After that, sign-up is invite-only: Workspace settings → Invite → copy the link and send it to your partner yourself (no email sending in v0.1).
3. User settings → API token → copy the MCP config snippet (`https://<app>/api/mcp` + bearer token).

**Mac app:** on first launch it asks for the server URL (the web app URL). It reads `GET /api/instance` (`{ name, convexUrl, convexSiteUrl, serverVersion, minAppVersion, needsSecret }`), then shows sign-in. Better Auth needs the Tauri webview's origin trusted (cross-domain plugin; spike in M2). If the server is older than the app supports, the app says "update your server" with a link to the docs.

**Updates and redeploys (self-hosters):**
- Every push to the user's copy redeploys web + Convex functions together (Convex Vercel guide). A Vercel rollback to an older deployment doesn't rerun the build, so Convex keeps the newer functions: keep schema and function changes backward compatible (widen first, narrow later), or roll back by reverting the commit.
- Pulling upstream: since the clone isn't a GitHub fork, GitHub's "Sync fork" isn't available. The repo ships a `sync-upstream` GitHub Action (manual or weekly) that opens a PR in the user's own repo from the latest Pantry release tag; merging it redeploys. (This is repo maintenance for self-hosters, not a product GitHub integration.) Users who prefer can fork first and import the fork into Vercel instead.
- The Mac app updates itself from Pantry's GitHub Releases (Tauri updater), independent of the server.

**What costs nothing** (personal, small team):
- **Vercel Hobby** (free; non-commercial personal use only, per Vercel's Hobby docs): per month 1M function invocations, 4 active-CPU hours, 360 GB-hrs provisioned memory, 100 GB fast data transfer, 1M CDN requests; 1-hour runtime logs; can't connect repos owned by a GitHub organization.
- **Convex free plan** (convex.dev/pricing): per month 1M function calls, 0.5 GB DB storage, 1 GB DB I/O, 1 GB file storage, 1 GB egress, 20 GB-hours action compute.
- Two people plus a few agents should stay well inside both. Note for Kris: if your products are commercial, check whether running your own tracker on Hobby counts as commercial use under Vercel's fair-use rules.

**Troubleshooting checklist:**
- Build says no deploy key → the integration isn't connected for Production + Preview, or a "Custom Prefix" was set.
- App is blank or "no address provided to ConvexReactClient" → `NEXT_PUBLIC_CONVEX_URL` wasn't injected; the build command isn't the wrapper script.
- Sign-in fails with an origin or URL error → Convex `SITE_URL` doesn't match the URL you opened; redeploy after adding a domain, or open the production URL rather than a preview URL.
- "Missing BETTER_AUTH_SECRET" on the setup screen → the deploy key couldn't set env; run the shown one-liner.
- Vercel can't connect the repo → Hobby can't use repos owned by a GitHub org; clone to a personal account.
- Mac app "not a Pantry server" → use the web app's https URL, not the `.convex.cloud` URL; check `/api/instance` in a browser.
- MCP 401 → token revoked or the client isn't sending the `Authorization` header.
- Hit a free-plan limit → Convex dashboard usage page; a runaway agent loop is the usual cause (revoke its token).

### Schema (`packages/backend/convex/schema.ts`)
Index names follow Convex's `by_a_and_b` convention. The block below is the **target** schema. The Spaces release ships a transitional version that also accepts M2 rows (an M2 `projects` shape, optional `issues.spaceId`, the `project_context` doc), migrates them on deploy, and narrows back in a later release: see `docs/MIGRATIONS.md`.
```ts
import { defineSchema, defineTable } from "convex/server";
import { v } from "convex/values";

const via = v.union(v.literal("app"), v.literal("mcp"));
const category = v.union(
  v.literal("backlog"), v.literal("unstarted"), v.literal("started"),
  v.literal("review"), v.literal("done"), v.literal("canceled"),
);
// 0 none, 1 urgent, 2 high, 3 medium, 4 low (Linear's order)
const priority = v.union(v.literal(0), v.literal(1), v.literal(2), v.literal(3), v.literal(4));
const spaceKind = v.union(v.literal("product"), v.literal("client"));

export default defineSchema({
  workspaces: defineTable({ name: v.string(), slug: v.string(), createdBy: v.string() })
    .index("by_slug", ["slug"]),

  members: defineTable({
    workspaceId: v.id("workspaces"),
    userId: v.string(), // Better Auth user id (lives in the component, so a string)
    displayName: v.string(),
    avatarUrl: v.optional(v.string()),
    role: v.union(v.literal("owner"), v.literal("member")),
  })
    .index("by_workspace", ["workspaceId"])
    .index("by_user", ["userId"])
    .index("by_workspace_and_user", ["workspaceId", "userId"]),

  invites: defineTable({
    workspaceId: v.id("workspaces"),
    email: v.string(), // lower-cased
    tokenHash: v.string(),
    createdBy: v.id("members"),
    expiresAt: v.number(),
    acceptedAt: v.optional(v.number()),
    revokedAt: v.optional(v.number()),
  })
    .index("by_token_hash", ["tokenHash"])
    .index("by_email", ["email"])
    .index("by_workspace", ["workspaceId"]),

  // A product or a client (spec §5): owns the issue key, the counter, the context doc and the views.
  spaces: defineTable({
    workspaceId: v.id("workspaces"),
    name: v.string(),
    key: v.string(), // ^[A-Z][A-Z0-9]{1,9}$, fixed after creation in v0.1
    nextIssueNumber: v.number(),
    archivedAt: v.optional(v.number()),
    kind: v.optional(spaceKind), // "product" when missing
  })
    .index("by_workspace", ["workspaceId"])
    .index("by_workspace_and_key", ["workspaceId", "key"]),

  // An optional workstream inside a space ("LinkedIn", "Launch"). An issue is in at most one.
  projects: defineTable({
    workspaceId: v.id("workspaces"),
    spaceId: v.id("spaces"),
    name: v.string(), // unique per space among active projects, ignoring case
    color: v.optional(v.string()),
    sortOrder: v.number(),
    archivedAt: v.optional(v.number()),
  })
    .index("by_space", ["spaceId"])
    .index("by_space_and_name", ["spaceId", "name"]),

  statuses: defineTable({
    workspaceId: v.id("workspaces"),
    name: v.string(),
    category, // fixed after creation; name, colour and order are editable
    order: v.number(),
    color: v.string(),
  }).index("by_workspace_and_order", ["workspaceId", "order"]),

  labels: defineTable({ workspaceId: v.id("workspaces"), name: v.string(), color: v.string() })
    .index("by_workspace", ["workspaceId"]),

  issues: defineTable({
    workspaceId: v.id("workspaces"),
    spaceId: v.id("spaces"),
    projectId: v.optional(v.id("projects")), // must be in the issue's space
    number: v.number(),
    key: v.string(), // "PAN-42"
    title: v.string(),
    description: v.string(), // markdown, "" when empty
    statusId: v.id("statuses"),
    statusCategory: category, // copied from the status for fast category filters
    priority,
    assigneeId: v.optional(v.id("members")),
    creatorId: v.id("members"),
    labelIds: v.array(v.id("labels")),
    parentId: v.optional(v.id("issues")), // one level only
    dueDate: v.optional(v.string()), // "YYYY-MM-DD"
    sortOrder: v.number(), // fractional: new = midpoint of neighbours
    completedAt: v.optional(v.number()),
    updatedAt: v.number(),
  })
    .index("by_space_and_status", ["spaceId", "statusId", "sortOrder"])
    .index("by_space_status_and_completed", ["spaceId", "statusId", "completedAt"]) // recent done, unread old
    .index("by_project", ["projectId"])
    .index("by_assignee_and_category", ["assigneeId", "statusCategory"])
    .index("by_parent", ["parentId"])
    .index("by_workspace_and_key", ["workspaceId", "key"])
    .index("by_workspace_and_updated", ["workspaceId", "updatedAt"])
    .index("by_space_and_updated", ["spaceId", "updatedAt"]) // MCP list_issues by space
    .index("by_assignee_and_updated", ["assigneeId", "updatedAt"]) // MCP list_issues by assignee
    .searchIndex("search_title", { searchField: "title", filterFields: ["workspaceId", "spaceId", "projectId"] }),

  comments: defineTable({
    issueId: v.id("issues"),
    authorId: v.id("members"),
    body: v.string(),
    via,
    editedAt: v.optional(v.number()),
  }).index("by_issue", ["issueId"]),

  activity: defineTable({
    workspaceId: v.id("workspaces"),
    issueId: v.id("issues"),
    actorId: v.optional(v.id("members")),
    type: v.union(
      v.literal("created"), v.literal("status_changed"), v.literal("priority_changed"),
      v.literal("assigned"), v.literal("labels_changed"), v.literal("commented"),
      v.literal("title_changed"), v.literal("description_changed"), v.literal("parent_changed"),
      v.literal("due_date_changed"), v.literal("project_changed"),
    ),
    from: v.optional(v.string()),
    to: v.optional(v.string()),
    via,
  })
    .index("by_issue", ["issueId"])
    .index("by_workspace", ["workspaceId"]),

  docs: defineTable({
    workspaceId: v.id("workspaces"),
    spaceId: v.optional(v.id("spaces")),
    kind: v.literal("space_context"), // widen to "doc" later
    title: v.string(),
    body: v.string(),
    updatedBy: v.id("members"),
    updatedAt: v.number(),
  }).index("by_space_and_kind", ["spaceId", "kind"]),

  apiTokens: defineTable({
    userId: v.string(),
    workspaceId: v.id("workspaces"),
    memberId: v.id("members"),
    name: v.string(),
    tokenPrefix: v.string(), // first 8 chars, e.g. "pan_x7Kq", shown in the UI
    tokenHash: v.string(), // SHA-256 hex
    lastUsedAt: v.optional(v.number()),
    revokedAt: v.optional(v.number()),
  })
    .index("by_token_hash", ["tokenHash"])
    .index("by_user", ["userId"]),
});
```

### Server rules Claude Code must follow
- **Every public function** starts with `const me = await requireMember(ctx)` (helper in `convex/lib/auth.ts`: Better Auth user → `members` row, throws if missing). MCP functions use `requireToken(ctx, token)` instead.
- **Invite-only sign-up, enforced on the server:** in Better Auth's `databaseHooks.user.create.before`, throw `APIError` unless the instance has no members yet (setup) or a pending, unexpired invite exists for that email. Accepting the invite link creates the `members` row.
- **One place for the name:** product name, default issue key and token prefix live only in `packages/backend/convex/lib/brand.ts`: `{ name: "Pantry", defaultKey: "PAN", tokenPrefix: "pan_" }`, imported by the app, MCP tool descriptions, `/api/instance` and seed data. Nothing else hard-codes them in code; the README, Deploy button URL and Tauri `productName`/`identifier` are the only hand-edited places, so a later rename stays a one-file change plus those.
- **Secrets:** API and invite tokens are random 32 bytes, base64url, prefixed with `brand.tokenPrefix` (`pan_`) / `inv_`. Generate them in a Convex action (queries and mutations run deterministically, so randomness belongs in actions), store only the SHA-256 hash via an internal mutation, return the plain token once. Hashing uses `crypto.subtle`, which Convex's default runtime supports.
- **Writes:** every mutation that changes an issue writes `updatedAt` and one `activity` row; `via` is `"mcp"` when called through `packages/mcp`.
- **Issue numbers:** read and bump `spaces.nextIssueNumber` inside the create mutation.
- **One status-change helper:** `issues.move` and MCP `update_issue { status }` share it: sets `statusId` and `statusCategory`, sets or clears `completedAt`, puts the issue at the top of the new column (unless `beforeId`/`afterId` say otherwise) and writes one `status_changed` row. `issues.update` never changes status.
- **Sub-issues inherit the parent's space and project:** `issues.create` with `parentId` takes `spaceId` and `projectId` from the parent (reject a different `spaceId` or `projectId`), and `create_sub_issue` over MCP goes through the same helper. A new parent brings its project along; changing a parent's project moves its sub-issues; a sub-issue can't take a project of its own. Test it for both paths (a common bug in other trackers).
- **Projects belong to one space:** an issue's `projectId` must be an active project of the issue's space (reject anything else). Archiving a project leaves its issues in the space with no project (each an issue write: `updatedAt` and one `project_changed` row). Project names are unique per space among active projects, ignoring case, because MCP finds them by name.
- **Sub-issues stay one level, no loops:** one shared helper used by `issues.create`, `issues.update` (setting or changing `parentId`) and MCP `create_sub_issue` rejects a `parentId` that is the issue itself, a parent that already has a parent, or a new parent for an issue that already has sub-issues. Test each case (another common bug).
- **Agent writes stay in the token owner's workspace:** every MCP function resolves space, project, issue, status, label and assignee inside `token.workspaceId` only, and returns "not found" (never another workspace's data) otherwise. Add one cross-workspace test per tool, even though v0.1 has one workspace per instance.
- **Env vars:** declare them in `convex/convex.config.ts` (`defineApp({ env: { … } })`, Convex validates declared vars at deploy time and generates a typed `env` import). Declare `SITE_URL` and `BETTER_AUTH_SECRET` as `v.optional(v.string())` in v0.1, not required: a required var that the deploy key can't set would fail `convex deploy` and the user would never reach the setup screen with its fallback one-liner. `auth.ts` throws a clear "Missing BETTER_AUTH_SECRET, see setup screen" error at runtime instead, and `/api/instance` reports `{ needsSecret: true }` so the setup screen can show the fix.

**Ordering (`sortOrder`):** new issues go to the top of their status (`min - 1`); a move between two issues takes the midpoint. When the gap between neighbours drops below `1e-9`, the mutation renumbers that status column to 1, 2, 3… in the same transaction. Fractional-index strings aren't needed at this size.

### MCP tools (`packages/mcp`)
Route: `apps/web/app/api/mcp/route.ts` = `withMcpAuth(createMcpHandler(registerTools), verifyToken, { required: true })`, exported as GET and POST. `verifyToken` hashes the bearer token and calls `mcp.verifyToken`; it returns `AuthInfo` with the member and workspace in `extra`, or `undefined` (→ 401). Tools read it from `ctx.http?.authInfo` and pass the raw token to each Convex function, which re-checks it, because these functions are public. `lastUsedAt` is updated by a separate mutation only when the stored value is over 10 minutes old.

All inputs are `z.object`. Issue keys match `^[A-Z][A-Z0-9]{1,9}-\d+$` (lower case is upper-cased first). Spaces are given by key (`PAN`); status, label, assignee and project are given **by name**, case-insensitive; `assignee` also takes `"me"` or `"none"`, and `project` takes `"none"`. Priority is a name (`none`, `urgent`, `high`, `medium`, `low`) or 0–4, and results show the name. The resolution itself runs in `convex/mcp.ts`, inside the token's workspace; `packages/mcp` turns a refusal into `isError: true` with its message. On bad input a tool returns `isError: true` with a message that lists the valid values (for example the workspace's status names, or the space's project names), so the agent can retry. Tool descriptions tell the agent to call `get_space_context` first, before starting work. The by-name lookups live in `convex/lib/spaces.ts` (`resolveSpaceByKey`, `resolveProjectByName`).

| `get_space_context` | `{ space }` (space key) | space name, key and kind, its active project names, context doc markdown, updatedAt, updatedBy |

An unknown project is an error listing the space's project names. Default status: the first `unstarted` status. Unknown labels are an error; labels are never auto-created |

- **Cloudflare one-click hosting (post-launch). Feasibility checked 26 Oct 2026: workable, not for v0.1; rough effort 2-4 days plus a Workers smoke test in CI.**
  - *Works:* [`@opennextjs/cloudflare`](https://opennext.js.org/cloudflare) (npm 1.20.13, peer `next >=16.4.1`, matches our pin) runs App Router, Route Handlers, SSR, middleware and `after` on the Workers Node.js runtime. Not supported yet: Node Middleware, so keep `middleware.ts` Edge-compatible. Better Auth runs inside Convex (the Next route only proxies), so it should not care about the host. `mcp-handler` 2.x uses Web `Request`/`Response` and dropped Redis ([README](https://www.npmjs.com/package/mcp-handler)), so `/api/mcp` should run on Workers, but this isn't documented anywhere: test it.
  - *Deploy to Cloudflare button* ([docs](https://developers.cloudflare.com/workers/platform/deploy-buttons/), updated 12 Oct 2026): clones the repo into the user's GitHub/GitLab, builds with Workers Builds, auto-provisions Cloudflare resources from the Wrangler config, and asks for secrets listed in `.dev.vars.example` / `.env.example` (descriptions via `cloudflare.bindings` in `package.json`). It can't create a Convex project. Monorepos aren't fully supported: a subdirectory must be self-contained, so point the button at the repo root with a root `wrangler.jsonc` and a build script that builds `apps/web`. Unverified: whether a button-prompted secret is visible at build time (`convex deploy` needs the key then); fallback is a build variable the user adds once.
  - *Images:* `next/image` optimisation needs a Cloudflare Images binding (may cost) or a custom loader ([OpenNext images](https://opennext.js.org/cloudflare/howtos/image)); simplest for us is `images.unoptimized: true`, since the app has few images.
  - *Limits* ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)): Free plan is 10 ms CPU per request and 100k requests/day; Cloudflare says SSR and auth "typically use 10-20 ms", so server-rendered pages may hit error 1102 on Free. Keep pages client-rendered against Convex, or recommend Workers Paid. Worker size is 64 MiB uncompressed on both plans per Cloudflare's page (OpenNext's docs still quote 3/10 MiB compressed; measure in the spike).
  - *Convex without Vercel's integration:* follow Convex's [custom hosting](https://docs.convex.dev/production/hosting/custom) pattern: the build runs `npx convex deploy --cmd "<OpenNext build>"`, which sets the Convex URL env var for the frontend build. `BETTER_AUTH_SECRET` / `SITE_URL` use the existing setup-screen fallback.
  - *User steps:* (1) create a Convex project and copy its production deploy key; (2) click Deploy to Cloudflare and paste it as `CONVEX_DEPLOY_KEY`; (3) open the `workers.dev` URL and finish the setup screen.
